## What the WTW test showed

Posting: 2027 Software Developer Internship, Reigate, UK. The calibrated model ran on 31 visible public description/qualification passages with real adjacent context.

Three confidently wrong sponsorship predictions were:

- Diversity/equal-opportunity paragraph: `available`, 91.28%.
- Closing date: `unavailable`, 92.77%.
- Offer/onboarding heading: `available`, 93.66%.

The visible text stated no explicit sponsorship policy. The existing decision projection returned `Could not verify` because of uncertainty/conflicts, not because every passage was interpreted correctly. The deterministic baseline returned `No blocker found`, which also does not prove sponsorship availability.

The training set lacked ordinary non-immigration negatives and `none`, `other-role` and `historical` scope examples. Its neighbor fields were empty, unlike this live inference. Diagnostics showed that neighboring application/onboarding language could amplify wrong sponsorship predictions; changing inference precision alone did not resolve the problem.

Keep WTW as exposed regression/development evidence, not a fresh held-out test. This was a worker/posting-text test, not a verification of the installed extension's automatic extraction or applicant forms. See [saved WTW evidence](evaluation/laya-training/live-job-tests/wtw-202605435/README.md).

## Agreed direction for the next model

Start with one checkpoint loaded once, performing two tasks:

1. Relevance screening: identify immigration sponsorship, visa eligibility, CPT/OPT and related employment-authorization restrictions. Forward relevant **and uncertain** passages.
2. Interpretation: answer the existing five fields for forwarded targets, using original unfiltered neighbors and the authoritative decision rules.

This is not independent verification: one shared model can make correlated errors. Improve the interpretation stage as well as adding the screen.

Important safeguards:

- Citizenship, clearance, export-control and other deterministic blocker checks keep receiving unfiltered posting text.
- Relevant applicant questions, company/historical policies and other-role policies do not automatically establish current-role sponsorship.
- Keep the five label vocabularies unchanged. The current v1 parser requires five answers for every block; introduce an explicit versioned transport change for skipped passages and update all callers together.
- Return a status for every original passage ID. Skipped/failed/unsupported interpretation is not a successful five-field answer and must not receive invented confidence.
- Keep actual posting neighbors after filtering. Do not join unrelated surviving passages or silently truncate policy conditions.
- Calibrate screening and interpretation deliberately. The installed temperature array is keyed by question type, not automatically by stage or field.

- Never train weights on calibration or test data, overwrite frozen datasets/checkpoints, or silently change historical split membership. Use new versioned artifacts.
- Do not treat the calibrated model as already active in the extension, or treat an uncertain final headline as proof of correct passage predictions.
